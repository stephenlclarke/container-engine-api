# Change handoff: cache verified provider-session peer identities

## Summary

Cache successful strict macOS peer-code validations per exact process instance so the one-connection-per-request provider protocol retains its authentication guarantees without repeating an expensive static-code scan for every Docker API request.

## Implementation

- Resolve `LOCAL_PEERPID`, the socket peer audit token, the executable path, and `PROC_PIDTBSDINFO` start time for every new connection.
- Key cached evidence by PID, the complete opaque audit token, start seconds, start microseconds, and executable path so PID reuse and every `exec` miss the cache without parsing token internals.
- Serialize the first strict validation for an unseen process instance and cache only its successful result.
- Bound each process-local cache to 32 entries with deterministic oldest-entry eviction.
- Preserve the client and server comparisons between the protocol-claimed identity and the independently resolved peer identity on every connection.
- Add focused tests for exact reuse, recycled PIDs, changed executable paths, failed loads, and capacity eviction.

## Validation

The focused `ContainerEngineProviderSessionTests` suite passes all 22 tests. A matched signed Container release build passes the terminal-session behavior and <10× timing gate in 1.238173 seconds on its first post-start capture and 0.920554 seconds warm, down from 4.359129 seconds before the cache; the pinned Docker fixture is 0.184992 seconds.

## Compatibility

There are no wire-format, public API, or persistence changes. The cache changes only how a successful peer identity is resolved after the first connection from one exact running process.

## Linked issue

Closes [#18](https://github.com/stephenlclarke/container-engine-api/issues/18).

## Remaining risks

The implementation deliberately retains the existing one-provider-connection-per-Docker-request protocol. The candidate is now inside the programme's <10× failure threshold but remains 4.98× slower warm than this short Docker reference case, primarily because its first pre-start attach boots the VM-backed runtime. A future persistent multiplexed provider transport and runtime-start optimization can reduce the remaining overhead; neither is required to remove the repeated code-signature bottleneck fixed here.
